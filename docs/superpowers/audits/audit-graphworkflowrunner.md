# Audit: GraphWorkflowRunner PHP → TS parity gap

- PHP (canonical): `backend/src/AgentTeam/Services/GraphWorkflowRunner.php` (3477 lines)
- TS (port): `backend_typescript/src/AgentTeam/GraphWorkflowRunner.ts` (1356 lines)
- Audited: full read of both files, plus supporting classes (`ExecutionTraceStore`, `StreamContext`, `SkillToolBridge`, `WorkflowRunLog`, `SkillToolChoice`, `NodeLogFormat`) on both sides.

## 1. High-level summary

The TS port is a faithful, well-documented replica of the **sequential** execution path (Start → agent → output, `runAgentWithClientToolBridge`, merge strategies, cost/pricing, output-schema post-hoc parsing, execution records). Its own header comments already self-declare several deferred items, and those declarations check out.

The single biggest divergence is the **TRUE-parallel executor**. In PHP, `executeAgentsInParallel()` (~line 1712–2057) is a completely separate, self-contained implementation that does NOT call `AgentRunner` — it drives `curl_multi` directly via `ProviderRequestFactory`, runs up to **10 tool-call rounds** per fan-out batch, forces `run_skill_script` via `SkillToolChoice`, emits every branch's skill call immediately and awaits them all concurrently (true fan-out), and only falls back to a "never completed" sweep at the round cap. The TS port's `executeAgentsInParallel()` is a **single-shot `Promise.all(agentRunner.run(...))`** with no tool-round loop, no skill-tool declaration, and — critically — **it never checks `result.pending_client_tool_call`**, so a parallel skill-bound node silently drops the skill call instead of round-tripping to the browser. This is a functional bug, not just a missing nicety: any workflow with 2+ parallel skill-bound agent nodes will misbehave in TS today.

Second-largest gap: several PHP dependencies are either entirely absent in TS (`WorkflowOutputStorage`, `SessionSearchService`, `WorkflowRunLog`, `SkillToolChoice`) or present-but-unwired (`ExecutionTraceStore.ts` exists fully ported with `insert()`, but `GraphWorkflowRunner.ts` never calls it). Combined effect: TS workflow runs (a) never persist output to disk storage, (b) never archive to `conversation_contexts` (missing from chat sidebar / session search), (c) never write the per-run JSONL debug log, and (d) never persist execution traces to the DB (self-healing / Phase 0 telemetry is blind for TS-run workflows) even though the storage class for (d) is ready to use.

Third: document handling. PHP's `buildDocumentsContext`/`readDocumentContent` is a full pipeline (universalFS adapter, local fallback, PDF text extraction via `pdftotext`/regex fallback, image detection for multimodal, scratch-file short-circuit for skill workflows). TS's `buildDocumentsContext` is explicitly a no-op stub that always returns `''` when documents are present (only the "no documents" path is exact).

Below is the itemized list, ordered by importance (functional/correctness impact first, then observability/data-durability, then completeness/cosmetic).

## 2. Concrete gaps

### 2.1 [CRITICAL] Parallel skill-bound nodes drop client-tool calls entirely
- **PHP**: `executeAgentsInParallel()` (php:1712-2057) builds a real multi-round tool loop (`maxRounds = 10`) per fan-out batch via `makeParallelLLMCalls()` (curl_multi + `ProviderRequestFactory::buildRequest/parseResponse`, php:2062-2223). Any `tool_calls` in a round are inspected; client-side tools (`run_skill_script`, `discover_skill`, `Task` — `isClientSideToolName()`, php:2230-2233) are stamped with a bridge-compatible id, **emitted immediately** via `emitClientToolCallInParallel()` (php:2253-2277, no blocking), collected into `$pendingClientAwaits`, and only **after the whole round's emits are done** are they awaited concurrently via `awaitClientToolResultInParallel()` (php:2288-2314, 120s cap via `config['parallel_skill_timeout_ms']`, default 120000). This is exactly the "emit-all then await-all" pattern called out in the task brief. A `skill_ran` run-once guard (php:1951-1962) stops the model from re-invoking the skill after the first round and instead nudges it to summarize.
- **TS**: `executeAgentsInParallel()` (ts:940-1085) dispatches `agentRunner.run(...)` once per branch via `Promise.all`/`.then` tagging (ts:1047-1058), then in the completion loop only branches on `result.success === false` vs. else-branch `result.text` (ts:1064-1081). **`result.pending_client_tool_call` is never read** — a parallel node whose skill call comes back pending is treated as if it finished with empty/partial text. There is no tool-round loop, no `run_skill_script` tool declaration for parallel nodes (see 2.2), no concurrent emit/await, no run-once nudge, no 120s parallel-skill cap, and no "never completed" sweep (PHP's dead-letter handling at php:2031-2053 that surfaces the last assistant text and marks `success=false` after `maxRounds`).
- **Porting notes**: TS's `AgentRunner.run()` already resolves *server-side* tools internally in a loop (matches PHP's sequential `AgentRunner`), so the fix is not "reimplement curl_multi" — Promise.all already gives real concurrency in Node. The missing piece is: (a) declare `run_skill_script` + force `tool_choice` for skill-bound parallel nodes (mirror 2.2), (b) after each `agentRunner.run()` resolves, check `pending_client_tool_call`; if set, emit `client_tool_call` and continue a per-branch round loop (bounded, e.g. 10) instead of finalizing, (c) restructure to emit-all-pending-skill-calls-then-await-all per round so branches within a round stay concurrent, (d) add the `parallel_skill_timeout_ms` 120s default for the parallel await path (currently only the sequential path's 60s default exists in TS, ts:734).
- **Missing dependency**: `SkillToolChoice.php` (php: `AgentTeam\Services\SkillToolChoice::forProvider($provider)`) has no TS equivalent — needed for step (a). It's a small pure-value builder (~30 lines), trivial to port.

### 2.2 [HIGH] Parallel path never declares `run_skill_script` to skill-bound agent nodes
- **PHP**: php:1848-1861 — for each node in the parallel init loop, if `getBoundSkillScripts($config)` is non-empty, `$tools[] = $this->buildRunSkillScriptTool(...)` is appended to that agent's tool list and `$forceSkillFirstRound = true` is set, later consumed by `makeParallelLLMCalls()` to inject `SkillToolChoice::forProvider(...)` into the raw request payload (php:2074-2079).
- **TS**: `executeAgentsInParallel()` builds only `toolsFilterFor(state)` (ts:1036-1041) and passes `{ workflow_execution_id, node_id, tools_filter }` to `agentRunner.run()` (ts:1049-1053) — no `extra_tools`, no `skill_metadata`, no `tool_choice`. Skill-bound parallel nodes are never told the tool exists.
- **Porting notes**: reuse the already-ported `getBoundSkillScripts()` (ts:1187-1204) and `buildRunSkillScriptTool()` (ts:1212-1257) — both exist verbatim already, just not called from the parallel path. This is the natural companion fix to 2.1.

### 2.3 [HIGH] `WorkflowRunLog` (per-run JSONL persistence) is entirely unported
- **PHP**: every `emitNodeEvent`/`emitWorkflowEvent` call persists the event to `storage/workflow-runs/<runId>.jsonl` via `WorkflowRunLog::append()` **before** the SSE emit (php:192-199, 235-241; constructed at php:91 `new WorkflowRunLog(WorkflowRunLog::defaultDir($config))`). This is what makes a run "debuggable after it ends/dies even with no browser attached" (per the class's own doc comment) — explicitly named in the task brief as a recent addition to verify.
- **TS**: `StreamContext.emitNodeEvent`/`emitWorkflowEvent` (ts StreamContext.ts:158-211) only forward to SSE; the file's own comment (line ~153) states "The WorkflowRunLog persistence PHP does [...]" is not implemented. `GraphWorkflowRunner.ts`'s `emitNodeEvent`/`emitWorkflowEvent`/`nodeLog` (ts:183-193) just delegate to `streamContext`, with no `runId`-keyed file write anywhere, and no `runLog` field exists on the class at all.
- **Porting notes**: needs a `WorkflowRunLog.ts` (append-only per-run JSONL writer, `fs.appendFile` with a lock-equivalent — Node has no `flock`, consider a write queue or `fs.promises.appendFile` which is atomic enough for line-append use) plus wiring into both `emitNodeEvent`/`emitWorkflowEvent`/`nodeLog` in `GraphWorkflowRunner.ts` (not just `StreamContext`, since PHP calls `runLog->append` at the point of emission regardless of whether `streamContext` exists — i.e. it must persist even when there's no live SSE listener, e.g. background/scheduled runs). `WorkflowRunLog::defaultDir()` resolves to `<backend>/storage/workflow-runs`; TS needs an equivalent default (`config.workflow_runs_dir` fallback).
- **Missing dependency**: `WorkflowRunLog.php` has no TS port.

### 2.4 [HIGH] `ExecutionTraceStore` DB persistence exists in TS but is never called (self-heal telemetry is blind)
- **PHP**: `recordExecutionTrace()` (php:998-1039) builds a full trace record (run_id, node_id, provider/model, skill_dir/script/argv, skill_exit_code/stdout/log_messages, output_files, final_text, success, tokens, cost) and calls `$this->traceStore->insert([...])`, both for sequential nodes (called from the main loop at php:454-457) and parallel nodes (called from `finalizeParallelNode()` at php:1703-1705).
- **TS**: `recordExecutionTrace()` (ts:1276-1287) is reduced to a comment ("ExecutionTraceStore.insert is STUBBED. Still emit the node_trace SSE event.") and only calls `emitNodeTraceEvent()` — no DB write. Yet `backend_typescript/src/AgentTeam/ExecutionTraceStore.ts` is a **complete, already-ported class** (447 lines: `insert`, `classify`, `outcomeQuality`, `diagnose`, `recommend`, `estimateHealCost`, etc.) with a working `insert(t: Trace): Promise<number|null>`. `GraphWorkflowRunner.ts` doesn't import or instantiate it anywhere.
- **Porting notes**: This is the cheapest high-value fix in the whole report — instantiate `new ExecutionTraceStore()` in the constructor (mirroring php:84) and call `.insert({...})` with the same field mapping PHP uses, in both the sequential (`recordExecutionTrace`) and parallel (`finalizeParallelNode`) call sites. No new class needs to be written.

### 2.5 [HIGH] `node_trace` skill fields are always null — `skillResultByNode` captured but never read back
- **PHP**: `recordExecutionTrace()` pulls `$sr = $this->skillResultByNode[$nodeId] ?? []` and populates `skill_exit_code`, `skill_stdout`, `skill_log_messages`, `output_files` from the actual bridge result stashed during the tool round-trip (php:1002-1038).
- **TS**: `this.skillResultByNode[...]` IS populated during `runAgentWithClientToolBridge()` (ts:757-761, sequential path only), but `emitNodeTraceEvent()` (ts:1263-1274) hardcodes `skill_exit_code: null, skill_stdout: null, skill_log_messages: null` unconditionally — it never looks up `this.skillResultByNode[node.id]`. So even sequential skill-bound nodes emit a `node_trace` event with empty skill telemetry today, contradicting the class's own stored data.
- **Porting notes**: fix `emitNodeTraceEvent`/`recordExecutionTrace` to read `this.skillResultByNode[phpIntval(node.id)]` the same way PHP does, for both sequential and (once 2.1/2.2 land) parallel nodes.

### 2.6 [MEDIUM] `WorkflowOutputStorage` (disk output persistence) unported
- **PHP**: on successful completion, `run()` calls `$this->outputStorage->saveOutput(...)` (php:544-566), best-effort (wrapped in try/catch, logs but never fails the run), writing execution metadata to disk storage; the result is included in the API response's `storage` field.
- **TS**: `run()` sets `const storageSaveResult = null;` unconditionally (ts:420-422) with a comment marking it stubbed. No `WorkflowOutputStorage.ts` exists.
- **Porting notes**: needs a new class port of `WorkflowOutputStorage.php` (not read in this audit — check its own file for FS/adapter dependencies, likely similar universalFS-or-local-fallback shape to `readFileRaw`).

### 2.7 [MEDIUM] `archiveRunToConversationContexts` (chat-sidebar / session-search archival) unported
- **PHP**: on successful completion, best-effort archives the run into `conversation_contexts` so it's visible in the chat sidebar and searchable (php:571-581, full implementation php:3292-3476: `archiveRunToConversationContexts`, `buildArchiveOutput`, `pickMarkdownAgentOutput`, `isHtmlShaped`). Includes HTML→Markdown conversion via `League\HTMLToMarkdown\HtmlConverter` with a walk-back heuristic fallback that picks the most recent non-HTML agent output if the End node's output is HTML-shaped or conversion fails/is unavailable.
- **TS**: no call, no equivalent method, not mentioned even in the stub comments at the top of the file (only `WorkflowOutputStorage` is explicitly called out — `archiveRunToConversationContexts` appears to have been missed by whoever wrote the port's deferred-items list, though the code comment at ts:420-421 does bundle it in as "both best-effort in PHP").
- **Porting notes**: needs `SessionSearchService`-equivalent DB access (`connectFromConfig`) plus an HTML→Markdown library for Node (e.g. `turndown` or `node-html-markdown`) to replace `league/html-to-markdown`. This is pure archival/UX — doesn't affect run correctness — hence Medium not High.
- **Missing dependency**: `SessionSearchService.php::connectFromConfig()` has no TS port (only used for this one call in this file, per the grep scope of this audit — didn't check other TS callers).

### 2.8 [MEDIUM] Document context building is a stub — attached documents never reach the agent
- **PHP**: `buildDocumentsContext()` → `readDocumentContent()` → `readFileRaw()` pipeline (php:2943-3270) supports: local-storage (File System Access API) documents via `scratchFilesByDocId` short-circuit (skill workflows) or `inlineDocuments` (generic agents) or a "stored locally, inaccessible" placeholder; remote documents via a universalFS adapter (`getDocumentStorageAdapter()`) with local-disk fallback; PDF text extraction via `pdftotext` shelling out with a regex-based fallback (`basicPdfTextExtract`); image detection (`isImageFile`) that's excluded from text context and instead surfaced via `getDocumentImages()` for multimodal (note: `getDocumentImages()` itself appears to have no caller within this file — possibly dead code or called from a subclass/trait not in scope of this audit).
- **TS**: `buildDocumentsContext()` (ts:927-934) is a hard-coded stub: if `documents` is non-empty it logs a warning ("document reading is DEFERRED (2a)") and returns `''`. The "no documents" path (`''` early return) is the only exact-matching branch. `scratchFilesByDocId`/`inlineDocuments` fields exist on the TS class and are populated from `run()`'s params (ts:213-219), but are **never read** — dead state.
- **Porting notes**: Given TS already receives `scratchFiles`/`inlineDocuments` as run() params and stores them, the "local storage" branches (scratch-file reference message, inline-document passthrough) are the highest-value/lowest-effort slice to port first — no filesystem adapter needed, pure string logic already mirrored in signature. The universalFS/PDF-extraction branches need real infra decisions (is there a TS universalFS client? is `pdftotext` available in the Node deployment env?) — flag these to the porting owner rather than assume equivalents exist.

### 2.9 [LOW-MEDIUM] Output-schema constrained decoding is not actually constrained
- **PHP**: `resolveOutputSchema()` result flows into `$runContext['output_schema']`, which `AgentRunner` presumably threads into the provider request for true constrained decoding (structured outputs / JSON mode) — not verified in this audit since `AgentRunner.php` was out of scope, but the schema is passed through to influence generation, not just post-hoc validation.
- **TS**: the port's own header comment (ts:35-36) states: "AgentRunner has no schema carrier, so the LLM is not actually constrained; the post-hoc JSON parse of the output is still reproduced." Confirmed: `resolveOutputSchema()` in TS (ts:1293-1323) is a faithful pure-data port, but whether `AgentRunner.ts.run()` forwards `runContext.output_schema` into the actual provider payload needs checking in `AgentRunner.ts` (out of scope here) — the GraphWorkflowRunner-level comment says it does not.
- **Porting notes**: this is an `AgentRunner.ts` gap surfaced through `GraphWorkflowRunner.ts`'s own docs, not a `GraphWorkflowRunner`-specific bug — flag to whoever owns `AgentRunner.ts` parity.

### 2.10 [LOW] `ensureDbConnection()` (PDO reconnect-on-drop) has no TS equivalent
- **PHP**: `ensureDbConnection()` (php:1609-1630) proactively pings (`SELECT 1`) and reconnects PDO + recreates `graphRepository`/`agentRepository`/`traceStore` after long-running LLM calls, called at php:368, 419, 505, 689, and inside `completeExecution`/`failExecution`. This guards against MySQL `wait_timeout` killing the connection during multi-minute LLM calls.
- **TS**: no equivalent — relies on the `db` pool (`backend_typescript/src/db/pools.ts`, Kysely-style) to handle reconnection transparently. This is very likely a non-issue for TS since connection pools (unlike a single long-lived PDO handle) typically re-acquire a fresh connection per query — but worth an explicit "confirmed fine" or "needs a keep-alive/retry wrapper" check against `pools.ts`'s actual pool config (idle timeout, retry-on-disconnect) rather than assuming.
- **Porting notes**: informational — flag for the `pools.ts` owner to confirm long LLM-call-duration query safety; not a `GraphWorkflowRunner.ts`-specific fix unless the pool doesn't already handle it.

### 2.11 [LOW] `executeAgentsInParallelNoTools` and `buildAgentLLMRequest`/`parseAgentLLMResponse` (deprecated no-tools parallel path) — confirm dead
- **PHP**: php:2413-2930 is an explicitly `[DEPRECATED]` parallel path (`executeAgentsInParallelNoTools`) plus its own hand-rolled per-provider request/response builders (`buildAgentLLMRequest`, `parseAgentLLMResponse`) — a full second implementation of parallel execution predating the tool-aware one. Not called from `run()` (only `executeAgentsInParallel` is invoked at php:338, 475).
- **TS**: correctly has no equivalent — this is dead code in PHP and rightly omitted. No action needed; noted here only so the porting owner doesn't mistake its absence for a gap.

### 2.12 [LOW] Minor logging/observability parity gaps (non-functional)
- PHP logs extensively via `error_log()` at nearly every branch of the traversal loop (queue state, node lookups, parallel detection, DB reconnects) — TS's sequential loop has almost none of this (only the explicit `node_log`/SSE-facing messages are ported). Doesn't affect behavior but makes TS harder to debug via server logs; the JSONL run-log (2.3) would substitute for most of this if ported.
- `NodeLogFormat.php` has 8 static formatters (`callingProvider`, `modelRequestedTool`, `modelRespondedText`, `runningSkill`, `skillFinished`, `skillTimedOut`, `completed`, `httpError`); TS's inline `NodeLogFormat` object (ts:44-65) only ports 6 — missing `modelRequestedTool` (needed for 2.1/2.2's tool-round loop) and `httpError` (needed if the parallel path's HTTP-error branch is ever ported, see 2.1).

### 2.13 [VERIFIED PARITY — no gap] Items from the brief confirmed present and correct in TS
- Sequential skill-bridge wait capped ~60s, configurable via `config.parallel_skill_timeout_ms` — ts:734, matches php:1208.
- Disabled-node no-op (`config.disabled`) in both sequential (ts:503-506) and parallel (ts:959-982) executors — matches php:670-673 and php:1740-1754.
- `node_log` milestone events from both sequential and parallel executors via a shared `nodeLog()` helper — ts:187-189 (delegates to `StreamContext.emitNodeLog`), matches php:208-217 in spirit (PHP's version also does `error_log` — see 2.12 for the logging-only nuance).
- Parallel nodes emit their outcome immediately via a `parallelEmitted` guard (`finalizeParallelNode`, idempotent) — ts:1087-1128, matches php:1661-1706 including the "no reference-corruption" idempotency guard.
- `node_trace` events carrying (attempted) skill data into the run log — wire event shape matches; **content is wrong** per 2.5.
- Every workflow event persisted... — **this is the one item from the brief that is NOT met**; see 2.3. Only the SSE-emit half is ported.
